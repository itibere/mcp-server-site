Chave de API na URL

Uma ferramenta interna de análise de documentos chamava uma API de LLM em nuvem com a chave na query string (?key=...). Sozinho, isso já é má prática. Somado a um tratamento de erro que mostrava a mensagem da exceção direto na tela, virou um vazamento esperando acontecer: bastava uma falha de rede pra chave aparecer no navegador de quem estivesse usando o sistema. O risco foi achado por acaso, durante o diagnóstico de um erro de indisponibilidade do fornecedor, e corrigido antes de qualquer exposição.

vetor segredo na URL + mensagem de exceção exibida ao usuário classe CWE-598 · CWE-209 status corrigido, sem exposição
01

O cenário

A aplicação é um web app Flask local: o usuário envia um PDF, o servidor extrai o texto e manda para a API do Google Gemini, que devolve uma análise. A tela começou a mostrar "Não foi possível obter resposta da API Gemini (todos os modelos indisponíveis)". A causa desse erro era externa (sobrecarga do fornecedor, HTTP 503 em todos os modelos testados). Mas, ao ler o cliente HTTP pra entender a mensagem, apareceu um problema bem mais sério do que a indisponibilidade.

02

O problema: duas decisões inofensivas que, juntas, vazam

A primeira peça estava no cliente da API. A chave ia montada dentro da URL, e qualquer erro de rede virava uma mensagem que incluía o texto original da exceção:

Antes: cliente da API
url = f"https://generativelanguage.googleapis.com/v1beta/models/{modelo}:generateContent?key={chave}"
try:
    resp = requests.post(url, json=payload, timeout=180)
except requests.RequestException as e:
    raise RuntimeError(f"Falha de rede ao conectar com a API Gemini: {e}")

A segunda peça estava na rota Flask, que devolvia qualquer exceção para o template como mensagem amigável:

Antes: rota da aplicação
except Exception as e:
    return render_template("index.html", erro=f"Erro ao processar o arquivo: {e}")

O elo que fecha a cadeia: quando a conexão falha, a biblioteca requests (via urllib3) gera uma mensagem no formato Max retries exceeded with url: /v1beta/models/...?key=AIza..., com caminho e query string completos. Queda de DNS, proxy corporativo, certificado inválido: qualquer um desses eventos comuns bastaria pra chave aparecer em texto puro no navegador, e dali em print de tela, chamado de suporte ou chat.

Nenhuma das duas decisões, isolada, parece grave. A chave na URL é um formato que o próprio fornecedor aceita. Mostrar o erro na tela é útil numa ferramenta interna. Juntas, formam o padrão descrito em CWE-598 (informação sensível em query string) combinado com CWE-209 (mensagem de erro com informação sensível).

A mesma leitura achou um bug menor, com efeito no mesmo ponto: o fallback de leitura da chave citava uma variável API_KEY que não existia. Sem a chave no .env, a aplicação quebraria com NameError em vez de avisar que a configuração estava faltando.

03

Antes de corrigir: a chave já vazou?

Achado um caminho de vazamento, a primeira pergunta é se ele já foi usado. Se sim, a correção de código não basta: a chave precisa ser revogada e trocada. A checagem cobriu os três lugares onde ela poderia estar:

Resultado da verificação
O .env está no .gitignore e nunca entrou em nenhum commit do histórico.
O valor da chave não aparece em nenhum commit (git grep em todas as revisões) nem em nenhum arquivo do projeto fora do .env.
O erro que motivou a investigação era de indisponibilidade (HTTP 503), cuja mensagem não inclui a URL. Não há registro de falha de rede, o único caminho que levaria a chave pra tela, nas execuções conhecidas.

Conclusão: a vulnerabilidade existia, mas não há sinal de que tenha sido disparada. Como a ferramenta roda localmente e só para uso próprio, trocar a chave ficou como medida opcional, não obrigatória. Numa aplicação exposta a outros usuários, o certo seria trocar mesmo assim, porque a ausência de registro não prova que o vazamento não aconteceu.

04

A correção

Depois: chave no header, erro sem detalhe da requisição
# A chave vai só no header: nunca na URL, que acaba em mensagens de exceção, logs e proxies.
headers = {"Content-Type": "application/json", "x-goog-api-key": chave}
url = API_URL.format(modelo=modelo)   # sem ?key=
try:
    resp = requests.post(url, json=payload, headers=headers, timeout=180)
except requests.RequestException as e:
    # Só o tipo da exceção: a mensagem completa pode carregar detalhes da requisição.
    raise RuntimeError(f"Falha de rede ao conectar com a API Gemini ({type(e).__name__}).") from None
1. Chave movida da URL para o header x-goog-api-key

Header é o canal previsto pelo fornecedor para autenticação. Ele não entra em mensagem de exceção de conexão, histórico de navegador, log de acesso de proxy nem cabeçalho Referer.

2. Mensagem de erro de rede reduzida ao tipo da exceção

É uma segunda camada de defesa: mesmo que algum dado sensível volte para a requisição no futuro, ele não sai pela tela. O from None descarta a exceção original encadeada, que carregaria a mensagem completa.

3. Fallback inexistente removido

Sem chave configurada, a aplicação agora mostra a mensagem prevista ("chave não configurada") em vez de quebrar com NameError.

4. De quebra: novas tentativas com espera crescente

Era o problema original. Agora HTTP 429, 500 e 503 geram até 3 tentativas por modelo (espera de 2 s e 4 s) antes de passar ao próximo. Timeout troca de modelo direto, para não empilhar esperas de 180 s.

A correção foi validada com testes que simulam a rede: uma falha de conexão cuja mensagem contém ?key=CHAVE-FALSA precisa gerar um erro que não contenha a chave, e todas as requisições precisam sair com a chave no header e nunca na URL.

05

Checklist: cuidado com chaves em qualquer aplicação

O caso é pequeno, mas o padrão se repete em qualquer integração com API paga: o segredo pode estar bem guardado no repositório e ainda assim vazar em tempo de execução. Pontos a checar:

1. Segredo nunca na URL

Use header (Authorization, x-api-key ou o equivalente do fornecedor) mesmo quando a API aceita ?key=. URL é o dado mais copiado, logado e exibido de uma requisição.

2. Exceção de biblioteca não vai crua para a tela

Mensagens de requests, drivers de banco e SDKs podem carregar URL, host, usuário e query. Na interface, mostre mensagem própria e, no máximo, o tipo do erro. O detalhe completo vai para log controlado, depois de filtrar segredos.

3. .env no .gitignore desde o primeiro commit, e .env.example sem valores

Se o segredo já entrou no histórico, apagar o arquivo depois não resolve: a chave tem que ser trocada.

4. Achou um caminho de vazamento? Verifique antes de corrigir

Procure o valor da chave no histórico do git, nos logs e nos arquivos gerados pela aplicação. Encontrou? Revogue e troque a chave primeiro, corrija o código depois.

5. Chave com o menor escopo possível

Restrinja a chave no console do fornecedor à API usada e, se der, a IPs ou referers, e defina cota ou alerta de gasto. Se vazar mesmo assim, o estrago fica limitado.

6. Teste que prova a ausência do segredo

Simule a falha com uma chave falsa conhecida e confira que ela não aparece na mensagem final. É barato e evita que uma refatoração futura traga o problema de volta sem ninguém perceber.

06

Status

Vulnerabilidade latente identificada e corrigida antes de qualquer exposição. A verificação confirmou que a chave nunca entrou no histórico do git nem em arquivos do projeto, e não há registro de falha de rede que a tivesse levado pra tela. O que fica do caso: diagnosticar um erro qualquer é uma boa hora de reler o caminho do erro inteiro, até onde a mensagem chega na tela.
