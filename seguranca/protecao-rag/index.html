Proteção de Endpoint de IA

Endpoints de IA (RAG, chat, embeddings) expostos publicamente costumam não ter nenhuma barreira contra chamada direta, fora do navegador — cada requisição custa dinheiro real. Como diagnosticar e mitigar, aplicável a qualquer backend de IA.

cobertura endpoint público de RAG mitigação rate limiting na borda status confirmado em produção
01

O risco

Um endpoint de IA público — chat com RAG, busca semântica, síntese via LLM — normalmente é chamado a partir de uma página web via fetch. É comum restringir isso por CORS (Access-Control-Allow-Origin) achando que isso "tranca" o acesso. Não tranca: CORS é aplicado pelo navegador de quem chama, não pelo servidor. Uma chamada direta via curl ou script ignora CORS completamente e chega normal no backend.

Sem outra barreira, cada requisição dispara chamadas reais — embedding numa API paga, inferência num modelo, consulta a um banco vetorial — cada uma com custo ou cota associada. Isso é uma superfície de abuso financeiro/exaustão de cota, não de roubo de credencial: ninguém precisa de chave nenhuma sua, só precisa saber a URL.

02

Como diagnosticar

Teste você mesmo, de fora do site, sem passar pelo frontend: bata direto no endpoint com curl. Se responder normalmente sem exigir nenhum token, chave ou desafio, o endpoint está aberto pra qualquer um que descubra a URL — inclusive por inspeção trivial do JavaScript da página, que precisa conter a URL pra funcionar.

Comandos
# SEU_ENDPOINT_IA = URL do Worker/função que atende o chat -- normalmente
# dá pra achar aberto no JS do frontend (ex: fetch(WORKER_URL, ...))
$ SEU_ENDPOINT_IA="https://seu-worker.workers.dev"

# chamada direta, sem passar pelo site -- sem token, sem header especial
$ curl -X POST "$SEU_ENDPOINT_IA" \
    -H "Content-Type: application/json" \
    -d '{"pergunta": "teste"}'

# se voltar 200 com resposta normal, o endpoint está aberto pra qualquer
# um que descubra a URL -- CORS no servidor não impede isso
Exemplo aplicado Endpoint de RAG que serve um dos chats do site respondia normalmente a chamada direta, sem nenhuma exigência de autenticação — mesmo com CORS restringindo a origem no cabeçalho. Confirmado com o mesmo comando curl usado nos testes internos de deploy.
03

Mitigação: rate limit na borda

Autenticação completa (login, API key por usuário) costuma ser exagero pra um chat público de site pessoal — muda a experiência de uso pra algo que não é o objetivo. O meio-termo prático é limitar por IP na borda, antes de qualquer chamada paga acontecer: um contador de requisições por janela de tempo, que barra com HTTP 429 quando estoura o limite, sem exigir nada do usuário legítimo.

A parte não óbvia: nem toda ferramenta de contagem "por borda" conta certo. Plataformas de edge/serverless otimizam pra escala global, o que frequentemente significa trocar consistência forte por velocidade — um contador pode existir e ainda assim deixar passar mais do que deveria, sem erro nenhum, sem avisar. Só se descobre isso testando de verdade, não lendo a documentação.

Exemplo aplicado — três tentativas, testadas de verdade
tentativa 1 — binding nativo de rate limit da plataforma: configuração aceita, mostrada como ativa no deploy. Em mais de 90 chamadas de teste (rajada e espaçadas ao longo de mais de um minuto), nenhuma foi bloqueada. Causa: esse tipo de contador fica em cache por nó de borda; em tráfego baixo cada chamada tende a cair num nó diferente, o estado quase nunca acumula.
tentativa 2 — contador próprio num key-value store: mesmo resultado, causa diferente — o store não garante que uma leitura veja uma escrita feita segundos antes por outra chamada, se caírem em nós de borda diferentes. 25 chamadas simultâneas leram todas o mesmo valor "zerado".
tentativa 3 — instância única e autoritativa por chave (Durable Object): toda chamada pra uma mesma chave (IP) conversa com a mesma instância, sem cache espalhado nem corrida. Rajada de dezenas de chamadas simultâneas: as primeiras passaram normalmente, o restante voltou HTTP 429 exatamente no ponto esperado pelo limite configurado — contagem batendo, sem sobra nem falta.
Comandos — tentativa 1, binding nativo (não bloqueou)
# wrangler.toml
[[ratelimits]]
name = "RATE_LIMITER"
namespace_id = "1001"

[ratelimits.simple]
limit = 20
period = 60

$ npx wrangler deploy

# teste: rajada paralela, conta quantos 200 vs 429 voltaram
$ for i in $(seq 1 25); do
    (curl -s -o /dev/null -w "%{http_code}\n" -X POST "$SEU_ENDPOINT_IA" \
      -H "Content-Type: application/json" -d '{"pergunta": "teste"}') &
  done
  wait
# resultado real: 25/25 em 200 -- o limite não pegou nenhuma
Comandos — tentativa 2, contador em KV (também não bloqueou)
$ npx wrangler kv namespace create RATE_LIMIT_KV

# wrangler.toml
[[kv_namespaces]]
binding = "RATE_LIMIT_KV"
id = "<id retornado pelo comando acima>"

// dentro do handler fetch, antes de chamar a API paga
const janela = Math.floor(Date.now() / 60_000)
const chave = `rl:${ip}:${janela}`
const atual = parseInt((await RATE_LIMIT_KV.get(chave)) || "0", 10)
if (atual >= 20) return new Response(..., { status: 429 })
await RATE_LIMIT_KV.put(chave, String(atual + 1), { expirationTtl: 120 })

$ npx wrangler deploy
# mesmo teste de rajada da tentativa 1 -- resultado real: 25/25 em 200 de novo

# limpeza depois de descartar a tentativa
$ npx wrangler kv namespace delete --namespace-id "<id>"
Comandos — tentativa 3, Durable Object (funcionou)
# wrangler.toml -- SQLite storage backend, elegível no plano free
[[durable_objects.bindings]]
name = "RATE_LIMITER_DO"
class_name = "RateLimiterDO"

[[migrations]]
tag = "v1"
new_sqlite_classes = ["RateLimiterDO"]

// src/index.js -- classe do Durable Object
class RateLimiterDO {
  async fetch() {
    const janela = Math.floor(Date.now() / 60_000)
    const registro = (await this.state.storage.get("contador")) || { janela: -1, contagem: 0 }
    const atual = registro.janela === janela ? registro.contagem : 0
    if (atual >= 20) return new Response(JSON.stringify({ success: false }))
    await this.state.storage.put("contador", { janela, contagem: atual + 1 })
    return new Response(JSON.stringify({ success: true }))
  }
}

// dentro do handler fetch principal, antes de chamar a API paga
const id = env.RATE_LIMITER_DO.idFromName(ip)
const stub = env.RATE_LIMITER_DO.get(id)
const { success } = await (await stub.fetch("https://rate-limiter/check")).json()
if (!success) return new Response(..., { status: 429 })

$ npx wrangler deploy

# mesmo teste de rajada -- resultado real: primeiras ~N em 200, resto em
# 429, contagem batendo exata com o limite configurado
$ for i in $(seq 1 25); do
    (curl -s -o /dev/null -w "%{http_code}\n" -X POST "$SEU_ENDPOINT_IA" \
      -H "Content-Type: application/json" -d '{"pergunta": "teste"}') &
  done
  wait

04

O que isso não resolve

Rate limit por IP não segura um ataque distribuído (muitos IPs, botnet) — só corta abuso casual e de fonte única, que é o cenário mais provável pra um projeto pessoal. Pra algo mais crítico, os próximos passos seriam desafio tipo Turnstile antes da primeira chamada, ou autenticação leve por sessão. Vale dimensionar a proteção pro risco real, não pro pior caso teórico — proteção demais também tem custo, em fricção de uso.

E a lição maior: "configurei um rate limiter" não é o mesmo que "o rate limiter funciona". As duas primeiras tentativas pareciam corretas — sintaxe certa, binding ativo, sem erro nenhum — e não protegiam nada. Só rajada de chamada real contra o endpoint em produção revelou isso.
