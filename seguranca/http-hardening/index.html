SEGURANÇA / HARDENING

HTTP Hardening

Auditoria de segurança HTTP feita neste mesmo site: nenhum incidente, nenhuma exploração — uma varredura deliberada em busca do tipo de furo que qualquer site estático "escrito na mão" tende a acumular sem perceber. Como cada um nasce, o que corrigimos e por quê.

cobertura 11 páginas HTML + 1 endpoint público + 1 app com SSO mitigação headers HTTP + CSP restrito + CDN oficial + rate limit + hardening de sessão status confirmado em produção
01

Onde esse tipo de furo costuma nascer

Não é sobre um bug isolado numa função — é sobre um padrão de construção que se repete em qualquer site estático montado sem build step, sem template compartilhado, página por página. Três hábitos concretos, encontrados nas próprias páginas deste site antes de hoje:

Tipo 1 — lógica de interface escrita direto num <script> dentro do HTML

Prático pra escrever rápido, mas isso obriga o Content-Security-Policy a incluir 'unsafe-inline' em script-src — e uma vez com isso ligado, o navegador executa qualquer script que aparecer inline no HTML, escrito pelo desenvolvedor ou injetado por um atacante via um bug de innerHTML não escapado. O CSP vira decoração. Encontrado em 9 das 11 páginas HTML deste site.

Tipo 2 — dependência de terceiro carregada de um link não oficial

Um <script src> que "funciona" nunca foi verificado se veio do canal público e documentado do fornecedor. Neste site, as 11 páginas carregavam o Tailwind de um caminho interno do Google (gstatic.com/antigravity/web/dev/...), não do CDN oficial — provável resíduo do ambiente de preview de uma ferramenta de desenvolvimento que vazou pro HTML publicado. Funciona até o dono do caminho decidir que não deveria.

Tipo 3 — endpoint próprio chamado via fetch(), "protegido" só por CORS

CORS é aplicado pelo navegador de quem chama, não pelo servidor — uma chamada direta via curl ou script ignora CORS e chega normal no backend. Sem outra barreira, qualquer um que descubra a URL (trivial: está no JavaScript da própria página) pode esgotar a cota paga de uma API de terceiro. Era o caso do endpoint de verificação de hash/link deste site.

02

O que corrigimos, passo a passo

a) Headers HTTP reais, não meta tag

Uma tentativa anterior de proteção usava <meta http-equiv="X-Content-Type-Options"> — que navegadores simplesmente ignoram; esse header só tem efeito como resposta HTTP de verdade. GitHub Pages (onde o site é hospedado) não permite configurar headers customizados. A saída: o domínio já passa pelo Cloudflare como proxy, então os headers entram via Transform Rule na borda, sem precisar de servidor próprio.

Antes → depois (curl -I https://itibere.tec.br/)
# antes: nenhum desses 5 headers presente na resposta real
✗ Strict-Transport-Security
✗ X-Content-Type-Options   # só existia via <meta>, sem efeito
✗ X-Frame-Options
✗ Permissions-Policy
✗ Content-Security-Policy

# depois: Cloudflare Transform Rule, "Add static header to response"
✓ Strict-Transport-Security: max-age=31536000; includeSubDomains
✓ X-Content-Type-Options: nosniff
✓ X-Frame-Options: DENY
✓ Permissions-Policy: geolocation=(), microphone=(), camera=()
✓ Content-Security-Policy: default-src 'self'; ...

b) CSP sem 'unsafe-inline' em script-src

Pra tirar 'unsafe-inline' sem quebrar as páginas, todo bloco <script> inline precisou virar arquivo externo primeiro — assets/ano.js (o rodapé com o ano, repetido em 8 páginas) e assets/checagem-hash-link.js (a lógica inteira da ferramenta de hash/link). Só depois disso o CSP pôde ficar restrito.

Antes → depois
<!-- antes: logica direto no HTML -->
<script>
  document.getElementById('ano').textContent = new Date().getFullYear();
</script>

<!-- depois: arquivo externo, mesma origem (self) -->
<script src="assets/ano.js" defer></script>

# header, script-src antes:
script-src 'self' 'unsafe-inline' https://www.gstatic.com

# header, script-src depois:
script-src 'self' https://cdn.tailwindcss.com

Sem 'unsafe-inline', um <script> ou atributo onerror= que um atacante conseguisse injetar via algum bug futuro simplesmente não executaria — o navegador recusa rodar qualquer script que não venha de uma origem explicitamente listada. style-src manteve 'unsafe-inline' propositalmente: o Tailwind via CDN injeta <style> em runtime pra aplicar as classes utilitárias, e evitar isso exigiria trocar a abordagem CDN por um build compilado — fora de escopo aqui.

c) Dependência trocada pro canal oficial

O script do Tailwind, presente nas 11 páginas, apontava pra gstatic.com/antigravity/web/dev/tailwindcss.min.js — um caminho sem documentação pública, quase certamente artefato do preview de uma ferramenta de desenvolvimento. Trocado pelo Play CDN oficial da Tailwind Labs (cdn.tailwindcss.com), documentado e com contrato público de estabilidade. Efeito colateral direto: o script-src do CSP deixou de precisar liberar o domínio gstatic.com inteiro (que hospeda um monte de coisa não relacionada do Google) — allowlist mais estreita, restrita a um domínio de propósito único.

d) Rate limit no endpoint público

O Worker que atende a ferramenta de verificação de hash/link (proxy pra API do VirusTotal) não tinha nenhum limite — CORS restringia origem no navegador, mas uma chamada direta via script passava reto e podia esgotar a cota paga da chave de API. Aplicado o mesmo padrão de Durable Object (instância única e autoritativa por IP, janela fixa de 60s) já detalhado no case Proteção de Endpoint de IA — não repetido aqui pra não duplicar conteúdo. Testado em produção: 10 chamadas passam, a 11ª volta HTTP 429.

03

Auditoria complementar: hardening de sessão e login (SSO)

Fora do escopo das 11 páginas estáticas acima: um app deste ecossistema que exige login de verdade (SSO via Google, sessão mantida no servidor por trás de um Worker) foi auditado especificamente contra bypass de autenticação e acesso indevido à interface. Resultado da auditoria: nenhum vetor de bypass encontrado — mas o padrão de hardening usado vale documentar aqui, porque é o checklist que separa "login de verdade" de "cadeado decorativo".

a) Identidade e sessão no servidor, nunca no cliente

Falha clássica de site estático "com login": a "sessão" existe só como variável JavaScript no navegador — forjável no devtools, e o conteúdo protegido continua saindo do servidor pra qualquer requisição, sessão ou não. A correção estrutural é mover o gate pro servidor: toda rota que serve conteúdo confere a sessão antes de renderizar qualquer coisa, e qualquer rota não reconhecida cai em 404 por padrão — default-deny, não default-allow.

b) Cookie de sessão com atributos corretos + payload assinado

HttpOnly (inacessível via JavaScript, mesmo se houver um bug de XSS), Secure (nunca trafega em HTTP puro) e SameSite=Lax (bloqueia envio em requisição cross-site não-GET). O payload (identidade + validade) vai assinado com HMAC-SHA256 usando uma chave que só existe como secret de servidor — alterar qualquer byte do payload invalida a assinatura, e a comparação da assinatura é feita em tempo constante (evita side-channel por tempo de resposta).

c) CSRF no próprio fluxo de login

OAuth tem sua própria superfície de CSRF: sem proteção, um atacante pode induzir a vítima a completar um login vinculado à sessão do atacante ("login CSRF"). Mitigado com um state aleatório de 128 bits, gerado antes do redirecionamento pro provedor de identidade, guardado em cookie assinado, e conferido em tempo constante contra o valor devolvido no callback.

d) Token de identidade validado na origem, nunca confiado vindo do cliente

O fluxo usado é Authorization Code (não Implicit): o código de autorização é trocado por um token de identidade numa chamada servidor-a-servidor autenticada por credencial de aplicação (nunca exposta ao navegador) — não existe caminho onde o cliente entregue um token pronto pro servidor aceitar sem essa troca. Emissor, audiência, expiração e verificação de e-mail do token são conferidos antes de qualquer decisão de acesso; o e-mail final passa por allowlist fechada, e a mensagem de erro de "não autorizado" é sempre genérica — não diferencia "conta não existe" de "conta existe mas não está na lista", pra não virar oráculo de enumeração.

e) Rate limit no fluxo de login

Mesmo padrão de Durable Object (instância única e autoritativa por chave) já usado no rate limit do endpoint da seção anterior, aqui aplicado por IP nas rotas de início e retorno do login: trava após N falhas numa janela, com tempo de bloqueio fixo. Não impede brute-force de senha (isso é problema do provedor de identidade, que já tem suas próprias proteções) — reduz ruído e tentativas automatizadas de martelar o fluxo de callback.

04

Frameworks e boas práticas seguidas

Cada correção acima mapeia pra uma categoria nomeada de referências públicas de segurança — não foi uma lista de tarefas arbitrária:

A02:2025 Security Misconfiguration — OWASP Top 10:2025. Cobre os headers HTTP ausentes/mal configurados corrigidos no passo (a).
A05:2025 Injection — OWASP Top 10:2025. O CSP restrito do passo (b) é mitigação direta contra XSS injetado, uma das formas de injeção cobertas por essa categoria.
A03:2025 Software Supply Chain Failures — OWASP Top 10:2025. Categoria que cobre exatamente o passo (c): depender de um caminho de distribuição não oficial pra uma biblioteca de terceiro.
API4:2023 Unrestricted Resource Consumption — OWASP API Security Top 10. O rate limit do passo (d) é a mitigação recomendada nessa categoria.
Secure Headers Conjunto de headers implementado (HSTS, X-Content-Type-Options, X-Frame-Options, CSP, Permissions-Policy) segue o baseline do OWASP Secure Headers Project e o HTTP Headers Cheat Sheet da OWASP Cheat Sheet Series.
CWE-1021 Improper Restriction of Rendered UI Layers or Frames — catálogo de fraquezas do MITRE. É a fraqueza estrutural por trás de clickjacking; X-Frame-Options: DENY e frame-ancestors 'none' no passo (a) fecham exatamente essa.
CWE-829 Inclusion of Functionality from Untrusted Control Sphere — catálogo de fraquezas do MITRE. Descreve com precisão o passo (c): carregar biblioteca de um caminho que não é o canal de distribuição pretendido pelo fornecedor.
Least privilege O token de API usado pra automatizar a purga de cache (fora do escopo deste case) foi escopado só pra "Cache Purge" numa única zona, nunca "All zones" — princípio geral de menor privilégio, não específico de nenhum framework citado acima.
A07:2025 Authentication Failures — OWASP Top 10:2025. Cobre os itens (a), (c), (d) e (e) da seção 03: gate no servidor, CSRF no login, validação de token na origem e rate limit de tentativas.
A04:2025 Cryptographic Failures — OWASP Top 10:2025. Cobre o item (b): assinatura HMAC-SHA256 do cookie de sessão e comparação em tempo constante.
CWE-352 Cross-Site Request Forgery (CSRF) — catálogo de fraquezas do MITRE. É a fraqueza estrutural por trás do login CSRF; o parâmetro state assinado no item (c) fecha exatamente essa.
CWE-613 Insufficient Session Expiration — catálogo de fraquezas do MITRE. A validade embutida e assinada no payload da sessão (item b) garante expiração real, não decorativa.
05

Resultado

Tudo confirmado em produção, não só configurado: headers reais conferidos via curl -I, CSP restrito testado ponta a ponta na ferramenta de hash/link sem quebrar nenhuma função, rate limit disparando 429 exatamente no limite configurado.

O motivo de cada item elevar a segurança de verdade, não só "marcar item de checklist":

  • Headers HTTP são aplicados pelo navegador, fora do controle de qualquer bug futuro no código da aplicação — uma camada de proteção que não depende de "lembrar de fazer certo" toda vez que alguém editar uma página.
  • CSP sem unsafe-inline transforma a política de segurança de "decorativa" em funcional: passa a barrar de verdade um script injetado, não só documentar a intenção.
  • CDN oficial remove uma dependência de infraestrutura que não estava sob controle nem contrato nenhum — o site parava de depender da boa vontade de um caminho interno do Google continuar acessível.
  • Rate limit protege disponibilidade e orçamento contra abuso automatizado, sem exigir login nem fricção nenhuma de quem usa a ferramenta normalmente.
