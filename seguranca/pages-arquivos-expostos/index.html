GitHub Pages publica mais do que o site

Um site estático hospedado no GitHub Pages dividia o repositório com scripts de um pipeline de coleta, arquivos de dados intermediários e configurações de deploy. O Pages não distingue o que é site do que não é: publica o repositório inteiro. Com isso, tudo ficava acessível por URL no domínio público. A dúvida inicial era outra, se valia a pena deixar o repositório privado para evitar cópia. A resposta levou a um problema mais concreto e a uma correção de poucos minutos.

vetor hospedagem estática que serve o repositório inteiro classe CWE-538 · CWE-552 status bloqueado, sem segredo exposto
01

A pergunta de partida: repositório privado impede cópia?

A preocupação era simples: com o repositório público, qualquer pessoa poderia copiar o site inteiro. A resposta curta é que deixar o repositório privado não impede isso. HTML, CSS, JavaScript e textos precisam chegar ao navegador para a página funcionar, e o que chega ao navegador pode ser salvo com "Salvar página" ou um wget -r.

O que um repositório privado esconde é justamente o que não é site: histórico de commits, código de automações e configurações. A pergunta certa, então, passou a ser outra: o que o site está servindo além do próprio site?

02

O achado: o domínio servia o repositório inteiro

No modo mais simples do GitHub Pages (publicar a partir de uma branch, com .nojekyll na raiz), todo arquivo versionado vira uma URL pública no domínio do site. Uma checagem de fora, sem login, confirmou (caminhos genéricos, representando cada tipo de arquivo):

Antes: resposta HTTP de caminhos fora do site
$ curl -s -o /dev/null -w "%{http_code}" https://exemplo.dev/<caminho>
/pipeline/coletor.py                 200   # scripts do pipeline de coleta
/pipeline/dados/lote_01.json         200   # dados intermediários
/scripts/gerar_pagina.py             200   # gerador de páginas
/workers/proxy/wrangler.toml         200   # config de worker serverless
/wrangler.jsonc                      200   # config de deploy
/.assetsignore                       200   # lista do que NÃO publicar (ironia)

Uma varredura nos arquivos versionados não achou chave, token nem senha. Então não havia segredo exposto, "só" código, dados e configuração que ninguém pretendia servir. Mesmo assim, é superfície desnecessária: um arquivo de configuração revela nomes de recursos, rotas e a estrutura da infraestrutura, o que ajuda quem quer mapear o ambiente. E basta um commit descuidado no futuro para um arquivo com segredo sair publicado no mesmo instante. O padrão se encaixa em CWE-538 (arquivo com informação sensível em diretório acessível externamente) e CWE-552 (arquivos acessíveis a partes externas).

03

As opções avaliadas

1. Bloquear os caminhos na borda (escolhida)

O domínio já passava pelo proxy do Cloudflare. Uma regra de WAF bloqueia os caminhos antes de chegar ao GitHub. É rápido, grátis e não mexe na hospedagem. Limite: o código continua visível no GitHub, porque o repositório segue público.

2. Repositório privado com hospedagem migrada

No plano gratuito do GitHub, o Pages exige repositório público. Tornar o repositório privado sem migrar antes derruba o site. Seria preciso publicar por outra plataforma (por exemplo, Cloudflare Workers com uma lista de exclusão de arquivos), apontar o DNS e só então fechar o repositório. Resolve mais, mas é uma troca de hospedagem de um domínio no ar.

3. Plano pago do GitHub

Permite Pages com repositório privado, mas não muda o comportamento central: o Pages continuaria servindo os scripts no domínio. Sozinho, não resolve o achado.

A escolha foi fechar o problema concreto primeiro, que era a exposição no domínio, e deixar a migração de hospedagem como decisão separada, sem pressa.

04

A correção: uma regra de WAF

Antes de bloquear, uma checagem: alguma página do site carrega arquivo desses caminhos? Bloquear algo que o site usa quebraria páginas no ar. A busca no HTML mostrou só links para o repositório no GitHub (instruções de git clone), nunca para o próprio domínio. Com isso confirmado, a regra foi criada no painel do Cloudflare, em Security rules → Custom rules, com ação Block:

Expressão da regra (caminhos genéricos)
(starts_with(http.request.uri.path, "/pipeline/")
 or starts_with(http.request.uri.path, "/scripts/")
 or starts_with(http.request.uri.path, "/workers/")
 or http.request.uri.path in {"/wrangler.jsonc" "/.assetsignore" "/.gitignore" "/.nojekyll"})

A regra ocupa 1 das 5 regras personalizadas do plano gratuito. Ela vale para todo o tráfego do domínio, inclusive o subdomínio www. e o endereço padrão usuario.github.io/repo/, que redireciona para o domínio próprio e cai no mesmo bloqueio.

Resultado, verificado de fora
Todos os caminhos fora do site passaram a responder 403, inclusive via www. e via o redirecionamento do github.io.
Home, páginas de projeto, cases, sitemap.xml e CSS continuam respondendo 200. Nenhuma página quebrou.
05

Aproveitando a revisão: o que um visitante vê no seu GitHub

Na mesma revisão, a pergunta "isto está exposto?" foi feita também sobre os repositórios privados. O detalhe que importa: olhar o próprio perfil logado não responde a pergunta. Logado, o GitHub mostra a visão de dono, com repositórios privados na lista e na atividade. A comparação certa é com uma consulta sem autenticação:

Dono logado × visitante sem login
                               dono logado          visitante
contagem de repositórios       todos                só os públicos
"Created N repositories"       lista os privados    só os públicos
URL de repositório privado     abre                 404 (nem confirma que existe)
e-mail do perfil               aparece              oculto

A opção "Private contributions", nas configurações do gráfico de contribuições, estava desligada. Assim, commits em repositórios privados nem entram como número no gráfico público. Mesmo ligada, ela mostraria só a contagem anônima, sem nome de repositório. Para ver o perfil como um estranho vê, abra uma janela anônima ou use curl na API pública sem token.

06

Checklist para quem hospeda site estático a partir de um repositório

1. Assuma que tudo no repositório vira URL

Publicar a partir de uma branch serve cada arquivo versionado. Teste de fora, com curl, os caminhos de scripts, dados e configurações.

2. Separe o que é site do que não é

O ideal é publicar só uma pasta de saída (/docs, dist/) ou fazer o deploy por workflow, enviando apenas os arquivos do site. Pipelines e automações podem morar em outro repositório.

3. Sem mudar a estrutura agora? Bloqueie na borda

Se o domínio já passa por um proxy com WAF, uma regra por prefixo de caminho fecha a exposição em minutos. Antes, confirme que nenhuma página depende desses caminhos.

4. Pasta nova, regra atualizada

O bloqueio por lista só cobre o que foi listado. Toda pasta nova que não seja site precisa entrar na expressão, ou volta a ser servida. É o ponto fraco dessa abordagem em relação à opção 2.

5. Repositório privado não é proteção contra cópia

O conteúdo publicado é público por definição. Se a preocupação é reaproveitamento, o que protege é a licença (um LICENSE com "todos os direitos reservados"), não a visibilidade do repositório.

6. Verifique exposição com os olhos de um estranho

Sessão logada engana. Use janela anônima, curl sem cookies ou a API sem token para saber o que o público realmente vê.

07

Status

Exposição bloqueada na borda e verificada de fora, sem nenhuma página do site quebrada. Nenhum segredo estava entre os arquivos expostos. O repositório segue público, porque parte dele é distribuída de propósito como código aberto. A migração para uma hospedagem que publique só a pasta do site fica como evolução futura, a ser decidida sem pressa.
